# 架构偏好:极简、被指标推着走

**偏好**: 架构默认极简,组件/层级能不加就不加。"成本控制、扛不住再说"——扩展是未来被实际指标逼出来的,不是设计时预设的。

**理由**: 预设的复杂度大多用不上,白白增加成本、运维负担、一致性/故障面。用户做的是要稳定盈利的业务系统,每一分基础设施成本都直接影响毛利。

**应用**:
- 提架构方案时**默认给最简可行版**,把更重的版本作为"扛不住时的演进路径"列出,而不是起点
- 要加任何组件/层级(缓存层、消息队列、分片、微服务拆分),必须说明它满足哪条具体判据(延迟/吞吐/热点/成本),不能只说"标准做法是"
- 警惕条件反射套模板:多级缓存、Kafka、K8s、读写分离——先问"这个负载真的需要吗"
- 扩展触发器写成"信号 → 动作"清单(如 CPU>70% → 加副本),让扩展被指标驱动
- 成本估算要给出来,让用户看见每个组件的月成本

**参见**: [[cache-tier-four-criteria]] 是这个偏好在缓存场景的具体判据。
