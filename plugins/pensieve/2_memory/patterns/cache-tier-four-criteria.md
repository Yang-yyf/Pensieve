# 加缓存层前的四条判据

**场景**: 设计存储/查询架构,看到"大数据量 + 需要缓存"就想套多级缓存(L1 进程内 + L2 Redis/Tair + L3 主存储)。

**错误**: 条件反射堆缓存层,没验证这个负载到底需不需要。每层都增加成本、缓存一致性复杂度、运维负担。

**正确**: 加任何一层缓存前,先验证四条判据,**至少一条成立**才加:
1. **延迟**: 底层存储延迟超 SLA
2. **吞吐**: 底层 QPS/吞吐扛不住
3. **热点**: 少数 key 被高频重复访问
4. **成本**: 缓存比底层便宜且能显著降底层负载(算总账)

四条全不成立 → 单层存储就够。进程内 L1 因零成本(共享进程内存、不引入组件)可作默认保留,但不是必须。

**后果**: NuoJing 在线决策服务,亿级存储但访问稀疏,我套了 L1 LRU + L2 Tair + L3 Lindorm 三层。被用户"为什么不直接全部用 Lindorm"点醒——Lindorm 单层 5-10ms < 10ms SLA,四条全不成立,L2 Tair 纯增成本+一致性复杂度。

**元教训**: 用户反复说"成本控制、扛不住再说",我嘴上答应、手上还堆复杂度。"被指标推着走、不预设"要落到每个组件决策,不是口头原则。
